# 데이터 출처와 연동 상태

> 이 문서는 "실제로 무엇을 확인했고, 무엇을 확인하지 못했는지"를 구분해서 기록한다. 확인하지
> 못한 항목을 확인된 것처럼 쓰지 않는다. 모든 확인일은 **2026-10-03**(1단계 설계 시점) 기준이며,
> 이후 재확인한 항목은 그 날짜를 별도로 적는다.

## 1. 활동 데이터 — 수집 방식

MVP는 **운영자 수동 등록 + CSV 가져오기 + 사용자 제보(운영자 승인 후 공개) + URL 가져오기
(1-A절)** 로만 활동을 등록한다. 자동 크롤링·스크레이핑(여러 공고를 목록에서 긁어오는 것)은
구현하지 않았고, 계획도 없다.

- 시드로 들어가는 22개 활동은 전부 `is_demo = true`로 표시되는 **가상 데이터**다. 실제 공모전·
  서포터즈·봉사·해커톤·창업·교육 프로그램이 아니며, 실제 주최기관("데모기관1"~"데모기관7")도
  존재하지 않는다. 운영 환경에는 이 시드를 넣지 않는다(아래 4절, `docs/operations.md`의
  "환경 분리" 참조).
- 운영자가 CSV로 가져오거나 직접 입력하는 활동도 `status = 'draft'`(CSV) 또는 운영자가 지정한
  상태로 시작하며, 공개(`published`) 전환은 운영자의 별도 조작이 필요하다.
- 사용자 제보(`submit_activity`)로 들어온 활동도 항상 `draft`로 시작하고 운영자 승인
  (`approve_activity_submission`) 전에는 비공개다(`/admin/submissions`).
- **자동 수집(공식 API/RSS/제휴)은 후속 확장이며 이번 범위에 포함하지 않았다.** 도입하기 전에
  반드시 확인해야 할 조건:
  1. 그 출처(학교 공지, 주최기관 홈페이지 등)의 이용약관·robots.txt·접근 정책이 자동 수집을
     허용하는지.
  2. 재배포 범위 — 원문 전체(포스터 이미지, 본문 전문)를 복제해도 되는지, 아니면 원문 링크 +
     직접 작성한 요약만 가능한지.
  3. 중복 식별 방법(URL 정규화, 출처 ID, 제목+주최기관+모집기간 조합)과 모호한 중복을 운영자가
     확인하는 절차.
  4. 수집 빈도·실패 처리·출처 변경(페이지 구조 변경) 감지 방법.
  이 조건들을 확인하기 전까지는 자동 수집을 추가하지 않는다 — 구현이 없다고 해서 "곧 할 일"로
  과장하지 않는다.

## 1-A. URL 가져오기(링크 붙여넣기 활동 등록) — 허용 출처 원칙과 금지 사항

운영자 활동 등록 화면과 사용자 제보 화면의 "URL로 가져오기"(`docs/architecture.md` 14장)는
위 4가지 조건 중 "자동 수집(목록을 따라가며 여러 건을 긁는 것)"과는 성격이 다르다 — **사람이
직접 고른 공고 1건의 URL을, 그 사람이 직접 요청한 순간에 1번만** 가져온다. 그래도 같은 원칙
(허용 출처·재배포 범위)을 지킨다.

**허용되는 출처:**
- 주최기관의 공식 홈페이지·공고 페이지.
- 학교(상명대학교 등) 공식 공지사항 페이지.
- 공개 API(공식으로 문서화되고 이용약관상 이런 용도의 호출이 허용된 경우).

**금지 사항:**
- **타 플랫폼(다른 대외활동 모음 사이트, 커뮤니티 등)의 목록 페이지를 출처로 쓰지 않는다.**
  그런 목록 자체가 이미 "재수집·재배포"의 결과물이라, 원 출처가 아닌 2차 출처를 긁으면
  출처 표시·이용 조건을 다시 추적할 수 없게 된다. URL 가져오기는 **운영자/사용자가 이미 원문
  공고 페이지라고 확인하고 붙여넣은 URL**만 다룬다 — 어떤 URL이 "원문인지 아닌지"를 시스템이
  자동으로 판별하지는 않으므로, 이 판단은 입력하는 사람의 책임이다.
- **목록 페이지를 따라가며 여러 공고를 자동으로 찾아내는 기능은 만들지 않는다.** 한 번의 요청은
  정확히 1개의 URL만 가져온다(`src/lib/activity-import/fetch.ts`의 `fetchSinglePage` — 이름부터
  그렇게 제한해 뒀다).
- **원문 전문이나 포스터 이미지는 저장하지 않는다.** 추출한 필드(제목·날짜 등)와 운영자/사용자가
  직접 작성·수정한 요약만 저장한다. 정기 점검(14.4절)도 매번 새로 가져와 그 자리에서 검사만 하고
  버리며, 재확인에 쓰는 것은 등록 시점에 저장해 둔 짧은 날짜 근거 문자열(`apply_end_at_evidence`)
  하나뿐이다.
- **robots.txt가 허용하지 않는 경로는 가져오지 않는다.** 식별 가능한 User-Agent
  (`SangmyungMateLinkImporter/1.0`)를 쓴다.

## 2. 상명대학교 재학생 이메일 도메인 — 부분 확인

| 항목 | 상태 |
|---|---|
| 확인 시도 | 2026-10-03, 공개 웹 검색 |
| 확인된 것 | `smu.ac.kr`이 상명대학교 **기관 공식 도메인**임(다수 학과 페이지의 공식 연락처 이메일에서 확인) |
| 확인하지 못한 것 | **재학생에게 실제로 발급되는 학생 웹메일의 정확한 도메인 형식과 발급 정책을 설명하는 공식 안내 문서 본문**. 시도한 URL들은 "이메일 무단 수집 거부" 상용구 페이지로만 연결됐다 |
| 반영 방식 | `app_settings.allowed_email_domains`(기본값 `["smu.ac.kr"]`)를 운영자가 Supabase Studio 또는 직접 SQL로 편집 가능한 설정으로 둠(하드코딩 아님). 실제 재학생 전용 도메인이 다르거나 추가로 있다면 이 값만 갱신하면 된다 |
| 재확인 필요 시점 | 운영 전환 전 — 상명대 정보화팀/학사팀에 직접 문의하거나 공식 발급 안내 페이지를 다시 찾아 확인할 것을 권장 |

**중요:** 이메일 인증은 "이 이메일 주소를 소유하고 있다"는 것만 증명한다. `smu.ac.kr` 도메인
이메일이라고 해서 그 사람이 **현재 재학 중**이라는 보장은 없다(졸업생이 계속 쓸 수도 있고,
서비스 운영 전까지는 이 허용 목록 자체가 검증되지 않은 추정값이다). `profiles.affiliation_self_declared`가
항상 `true`로 시작하는 이유이기도 하다 — 대학/캠퍼스/전공은 **자기기입**이며, `campus_verified`가
`true`가 되려면(현재 시드에서는 운영자가 수동으로 세팅) 별도의 더 강한 검증(학생증, 재학증명서
등)이 필요하다. 그 검증 수단은 이번 범위에 없다.

## 3. 서울캠퍼스 전공 목록 — 부분 확인

| 항목 | 상태 |
|---|---|
| 확인 시도 | 2026-10-03, https://www.smu.ac.kr/ko/intro/collegeStatus.do (공식 편제 현황 페이지) |
| 확인된 것 | 서울캠퍼스는 5개 단과대학(인문사회과학대학·사범대학·경영경제대학·융합공과대학·문화예술대학), 20개 학부(과), **22개 전공**으로 구성됨 |
| 확인하지 못한 것 | 22개 전공의 **전체 개별 명칭 목록** — 단과대학별 하위 페이지에 흩어져 있어 이번 조사에서 전부 모으지 못했다 |
| 반영 방식 | `majors` 테이블(고정 enum 아님, 운영자가 CRUD로 편집 가능)에 시드로 5개만 `is_demo = true`로 넣어뒀다. 실제 22개 전공 전체를 확보하면 운영자가 직접 추가하거나 SQL로 일괄 삽입하면 된다 |

## 4. 에브리타임 공식 연동 — 미확인 (가장 중요)

| 항목 | 상태 |
|---|---|
| 확인 시도 | 2026-10-03, 공개 웹 검색 + https://everytime.kr/ 공식 홈페이지 확인 |
| 확인된 것 | 없음 |
| 확인하지 못한 것 | 외부 서비스용 공개 OAuth/API 개발자 문서 |
| **이것이 뜻하는 것** | **공식 연동이 "존재하지 않는다"는 확정이 아니다.** 단지 이번 조사(공개 웹 검색 범위)에서 찾지 못했을 뿐이다 |
| 실제 구현 | 로그인은 **이메일 매직링크(OTP)만** 지원한다. 에브리타임 로그인 버튼, "에브리타임으로 가입" 같은 UI는 **어디에도 없다** — 작동하는 것처럼 보이는 가짜 버튼을 만들지 않는다는 원칙을 그대로 지켰다 |
| 인증 공급자 우회 여부 | 사용자의 에브리타임 자격증명을 받아 대리 로그인하지 않는다. 비공개 API·인증 우회·트래픽 역공학을 쓰지 않는다 |
| 확장 가능성 | `@supabase/supabase-js`의 Auth는 OAuth 공급자를 추가로 설정할 수 있는 구조이므로, 에브리타임이 향후 공식 OAuth를 제공하면 로그인 화면에 공급자를 추가하는 정도로 확장 가능하다. **단, 그 공식 문서·제휴 가능 여부가 실제로 확인된 뒤에만 추가한다.** 연결 시에도 로그인된 사용자의 명시적 동의와 공급자 계정 확인을 거치고, 닉네임이 같다는 이유로 계정을 자동 병합하지 않는다 |

## 5. 요약 — 운영 전환 전 재확인 체크리스트

실제 운영(실제 학생 대상 서비스)으로 전환하기 전에 아래를 다시 확인해야 한다:

- [ ] 상명대 재학생 웹메일의 정확한 도메인·발급 정책 (정보화팀/학사팀 문의)
- [ ] 서울캠퍼스 22개 전공의 전체 공식 명칭 (단과대학별 페이지 전수 확인)
- [ ] 에브리타임 공식 API/OAuth 제공 여부 (제공 시에도 공식 제휴·이용약관 확인 후 연동)
- [ ] 자동 수집을 도입한다면 위 1절의 4가지 조건
- [ ] 활동 자동 수집 출처로 쓸 각 주최기관·공지 페이지의 재사용 조건

이 체크리스트 항목이 확인되기 전까지, 관련 기능은 "운영자가 설정 가능한 자리만 마련됨" 상태로
유지한다(완료로 보고하지 않는다).
