# 상명대학교 서울캠퍼스 대외활동 추천 프로그램: 티처블 머신·전공 반영 가이드라인

작성일: 2026-10-13
개정: 서울캠퍼스 학과·전공 선택, 전공별 분야 연결, 복수전공·미배정 처리 및 전공 적합도 추천 추가.

전제: 활동 목록, 사용자 프로필, 추천 화면 등 기존 프로그램은 개발되어 있으며, 티처블 머신 모델과 연결하는 부분을 추가한다. 기존 코드와 실제 데이터는 검토하지 않았으므로 아래 내용은 기술 스택에 맞추어 적용할 설계안이다. 데이터 수, 학습 설정, 임계값, 평가 목표는 공식 권장값이나 측정 결과가 아니라 초기 실험을 위한 제안이다.

## 1. 개발 방향

티처블 머신은 **포스터 이미지에서 활동 분야 후보를 제안하는 분류기**로 사용한다. 최종 추천은 기존 프로그램에서 활동의 확인된 정보와 사용자가 입력한 전공·관심 분야·참여 선호를 비교하여 계산한다. 주요 대상은 상명대학교 서울캠퍼스 학생이다. 전공은 사용자가 선택하는 프로필 정보이며 이미지로 추정하지 않는다.

이미지 분류 모델이 포스터를 입력받는다고 해서 한글 문장을 읽고 모집 조건을 이해하는 것은 아니다. 특히 마감일, 지원 자격, 온라인 여부, 활동 기간, 팀 구성 조건은 이미지 분류 결과로 확정하면 안 된다. 이런 정보는 원문이나 관리자 입력으로 확보한다. 외부 도구 사용이 허용되면 OCR을 보조로 붙일 수 있지만, OCR 추출값도 확인을 거쳐 사용한다.

공식 문서에 따르면 티처블 머신은 이미지·소리·포즈 분류 모델을 만들고 외부 프로젝트에서 실행하는 도구다. 공개 이미지 라이브러리는 MobileNet을 사용하며, 분류 출력은 클래스별 점수다.[1][2][3][4] 이 구조를 고려하면 포스터의 의미를 정확히 이해하는 엔진으로 쓰기보다는, 분야 분류를 보조하는 역할이 적합하다.

### 역할 분담

| 작업 | 담당 | 저장 결과 |
|---|---|---|
| 포스터 분야 후보 분류 | 티처블 머신 | 전체 클래스 점수, 상위 후보 |
| 모집 조건 확인 | 원문 확인·관리자 입력, 선택적으로 OCR | 마감일, 대상, 지역, 일정 등 |
| 후보 검토·수정 | 관리자 | 확정 분야와 다중 태그 |
| 참여 가능 여부 판단 | 기존 프로그램 | 가능·불가·확인 필요 |
| 사용자별 순위 계산 | 기존 추천 로직 | 추천 점수와 추천 이유 |

티처블 머신 사용만 허용되는 과제라면, 다른 AI를 추가하지 않고 **티처블 머신 + 관리자 입력 + 규칙 기반 추천**으로 구현한다. 티처블 머신을 활용한다는 이유로 모집 조건까지 이미지로 추정할 필요는 없다.

## 2. 첫 모델은 4개 분야로 검증하고, 서비스 분야는 서울캠퍼스 전공을 포괄한다

활동 유형과 관심 분야를 같은 분류 축에 섞지 않는다. 예를 들어 ‘공모전, IT, 봉사, 디자인’을 한 모델의 클래스로 지정하면 IT 디자인 공모전이 동시에 여러 클래스에 해당한다.

아래 4개 분야는 이미지 분류 가능성을 확인하는 예비 모델의 범위다. 서울캠퍼스 전체 전공을 포괄하는 최종 서비스의 분야 목록으로 사용하지 않는다. 첫 모델은 다음과 같은 분야 구분으로 시작한다. 이는 분류 가능성이 보장된 구성이 아니며, 실제 포스터로 검증할 후보 체계다.

| 클래스 ID | 분야 | 주된 과업 기준 |
|---|---|---|
| IT_DATA | IT·데이터 | 개발, 데이터 분석, 기술 구현 |
| BUSINESS_PLANNING | 경영·기획 | 사업 제안, 마케팅 전략, 서비스 기획 |
| DESIGN_MEDIA | 디자인·미디어 | 시각 디자인, 영상·콘텐츠 제작 |
| SOCIAL_ENVIRONMENT | 사회문제·환경 | 사회문제 해결, 환경 실천·캠페인 |

**라벨은 원문을 읽고 붙인다.** 색상이나 그림만 보고 정답을 정하지 않는다. ‘파란 포스터는 IT’처럼 수집자의 편견을 정답에 반영하지 않는다.

복합 활동은 무엇을 주로 수행하거나 제출하는지 기준으로 대표 분야 하나를 정하고, 부가 분야는 별도 태그로 보관한다. 예를 들어 환경을 주제로 한 영상 공모전은 영상 제작이 주된 평가 대상이라면 DESIGN_MEDIA를 대표 분야로, 환경을 부가 태그로 지정한다. 어느 기준으로도 일관되게 분류되지 않는 자료는 첫 학습에서 보류한다.

활동 유형은 별도 필드로 저장한다. 예: 공모전, 서포터즈, 봉사활동, 교육, 대외 프로젝트. 첫 버전에서 유형 분류용 모델까지 추가하지 않는다.

공개 학습 코드의 출력층은 softmax다.[3] 따라서 한 모델의 ‘IT 0.6, 디자인 0.3’은 두 분야에 각각 독립적으로 해당할 확률을 뜻하지 않는다. 상위 두 결과는 후보이며, 다중 태그의 정답은 원문 확인으로 정한다. 사용자 성향과 활동 포스터를 한 이미지 모델에 함께 학습시키려 하지 않는다.

### 서비스용 활동 분야 태그

사용자 관심 분야와 전공 연결표에는 아래 12개 분야를 사용한다. 학교의 공식 학과 분류가 아니라 이 프로젝트의 추천용 분류 체계다. 활동 유형과는 별도로 관리한다.

| 분야 ID | 표시명 |
|---|---|
| IT_DATA | IT·AI·데이터 |
| ENGINEERING | 전기·전자·제조·공학 |
| BUSINESS_FINANCE | 경영·마케팅·금융 |
| HUMANITIES_CULTURE | 인문·역사·문화콘텐츠 |
| LAW_POLICY | 법·지식재산·정책·안보 |
| EDUCATION | 교육·멘토링 |
| SOCIAL_WELFARE | 복지·지역사회·사회공헌 |
| BIO_FOOD_HEALTH | 바이오·식품·영양·보건 |
| ENERGY_ENVIRONMENT | 에너지·소재·환경·도시 |
| DESIGN_MEDIA | 디자인·영상·애니메이션·게임콘텐츠 |
| ARTS_PERFORMANCE | 미술·음악·공연·무용 |
| SPORTS | 스포츠·운동·건강관리 |

이 분야 태그는 최초부터 원문 확인으로 등록할 수 있다. 티처블 머신은 충분한 데이터와 검증 성능을 확보한 분야부터 지원한다. 초기에 4개 모델 클래스만 있더라도 나머지 분야 활동을 정상 등록·추천해야 한다.

예비 모델의 BUSINESS_PLANNING은 BUSINESS_FINANCE의 일부를 다루며, SOCIAL_ENVIRONMENT는 정책·교육·복지·환경 중 어느 것인지 원문 확인이 필요하다. 클래스명 문자열을 서비스 분야 ID로 바로 저장하지 않고, 모델 버전별 후보 연결표를 둔다. 4개 모델 클래스를 12개 분야의 확정 태그로 자동 변환하지 않는다.

전공 수만큼 이미지 클래스를 만들지 않는다. 여러 전공이 같은 활동에 참여할 수 있고, 포스터만 보고 ‘상명대 특정 전공 대상’을 판단할 수 없기 때문이다. 모든 전공을 지원하기 위해 먼저 확장할 것은 프로필과 활동 태그이며, 이미지 모델의 클래스 확대는 분야별 데이터 확보 후 별도로 진행한다.

## 3. 먼저 소규모 실험으로 가능성을 확인한다

처음부터 수천 장을 모으기보다는 분야별 약 50장의 서로 다른 행사 포스터로 예비 실험을 한다. 이때도 학습용과 별도 확인용 자료를 분리한다.

서로 다른 기관에서 나온 처음 보는 포스터를 거의 구분하지 못한다면, 학습 횟수를 무작정 늘리지 않는다. 분류 기준의 중복, 데이터 편향, 글자 의존도를 먼저 확인한다. 개선되지 않으면 분야 수를 줄이거나 적용 범위를 좁히고, 자동 분류 대신 관리자 후보 제안 기능으로 사용한다. 포스터의 의미가 대부분 글자로 표현되는 데이터에서는 티처블 머신만으로 높은 분류 성능을 얻지 못할 수 있다.

예비 실험이 가능성을 보이면, 본 실험은 분야별 150~200개의 독립적인 행사 자료를 출발점으로 잡는다. 자료의 다양성과 정답 품질이 단순 이미지 수보다 중요하다.

### 본 실험 데이터 예시

분야별 200개, 총 800개 행사를 확보한 경우:

| 구분 | 분야별 개수 | 전체 개수 | 사용 목적 |
|---|---:|---:|---|
| 학습 자료 | 140 | 560 | 티처블 머신 학습에 업로드 |
| 개발 검증 자료 | 30 | 120 | 설정·임계값 선택 |
| 최종 시험 자료 | 30 | 120 | 설정 확정 후 최종 평가 |

실제 그룹 크기에 따라 수량은 달라질 수 있다. 티처블 머신 내부에서 보여주는 검증 결과와 별도로 외부 검증·시험 자료를 보관한다. 외부 자료는 학습 클래스에 업로드하지 않는다.

### 데이터 수집·분할 원칙

- 행사 ID, 행사 시리즈 ID, 주최 기관, 원문 URL, 수집일, 대표 분야, 이미지 경로를 기록한다.
- 같은 행사의 원본, 크기 변경본, SNS 홍보본, 재게시본은 같은 그룹으로 묶는다.
- 해마다 비슷한 디자인을 쓰는 같은 행사 시리즈도 가능한 한 같은 그룹에 둔다.
- 그룹을 먼저 나누고, 이후 전처리·증강을 한다. 증강본을 독립적인 행사 수로 세지 않는다.
- 한 분야가 특정 기관·로고·템플릿으로만 구성되지 않게 한다.
- 각 분야에 다양한 색상, 레이아웃, 글자 비율, 이미지 스타일을 포함한다.
- 별도로 학습에 없는 분야나 일반 광고 이미지를 모아, 범위 밖 입력에서 오분류가 얼마나 발생하는지 확인한다.
- 최종 시험 결과를 보고 다시 모델을 수정했다면 그 시험 자료는 개발 자료가 된 것이므로, 다음 최종 평가용 자료를 새로 확보한다.

## 4. 긴 포스터가 잘리지 않도록 전처리를 통일한다

공개 이미지 라이브러리는 작은 정사각형 입력을 사용하고, 예측 과정에서 cropTo 함수를 호출한다.[4] 세로로 긴 포스터를 그대로 넣으면 중요한 영역이 손실될 수 있으므로 실제 입력 결과를 확인해야 한다.

권장 전처리는 다음과 같다.

1. 화면 캡처에 포함된 브라우저 메뉴·사이트 테두리만 제거한다.
2. 포스터 본문은 종횡비를 유지한다.
3. 정사각형 캔버스 안에 전체 포스터가 들어가도록 배치한다.
4. 남는 공간을 모든 클래스에서 동일한 색으로 채운다.
5. 학습용 이미지와 서비스 입력에 같은 처리를 적용한다.

서비스에서만 여백을 추가하거나 학습 때만 특정 영역을 자르면 입력 조건이 달라진다. 전처리 규칙에도 버전을 부여한다. 정사각형 여백 추가는 전체 영역을 보존하는 방법이며, 축소된 작은 글자를 읽게 만드는 해결책은 아니다.

첫 모델에서는 과도한 회전, 좌우 반전, 글자 왜곡을 피한다. 필요한 경우 학습 자료에만 약한 밝기·압축 변화 등을 적용하고, 효과를 외부 검증 자료에서 확인한다.

## 5. 티처블 머신 학습·내보내기 절차

1. [티처블 머신](https://teachablemachine.withgoogle.com/)에서 이미지 프로젝트의 일반 이미지 모델을 선택한다.
2. 클래스 이름을 앞에서 정한 고정 ID로 지정한다.
3. 전처리한 학습 자료만 각 클래스에 업로드한다.
4. 우선 화면에 표시되는 기본 설정으로 학습하고 설정값을 기록한다.
5. 외부 검증 포스터를 입력해 결과를 저장한다.
6. 필요하면 epoch 30·50·80 등의 작은 비교 실험을 한다. 한 번에 한 설정만 바꾼다.
7. 검증 결과가 가장 좋은 설정과 판정 기준을 확정한다.
8. 마지막에 분리해 둔 시험 자료로 평가한다.
9. 웹 프로그램이라면 TensorFlow.js 형식으로 내보낸다.

모델 파일, 메타데이터, 가중치 파일을 함께 보관한다. model.json이 참조하는 가중치 경로를 유지한다. 실제 내보내기 예제와 호환되는 라이브러리 조합을 확인하고 버전을 고정한다. 오래된 예제의 버전과 최신 패키지를 무작정 혼합하지 않는다.

학습 프로젝트, 라벨 기준, 데이터 분할 목록, 설정값, 평가 결과도 함께 보관해야 다음 모델과 비교할 수 있다.

## 6. 기존 프로그램에는 ‘활동 등록 시 분석’을 추가한다

사용자가 추천 화면을 열 때마다 모든 포스터를 다시 분석하지 않는다. 활동이 등록되거나 포스터·모델 버전이 바뀔 때 분석하고 결과를 저장한다.

권장 흐름:

1. 관리자가 활동과 포스터를 등록한다.
2. 원문에서 모집 조건을 입력하거나 확인한다.
3. 정해진 전처리 후 티처블 머신이 모든 클래스의 점수를 반환한다.
4. 시스템이 상위 후보와 검토 상태를 저장한다.
5. 관리자가 원문과 비교하여 대표 분야 및 부가 태그를 확정한다.
6. 기존 추천 기능이 확인된 활동 정보와 사용자 선호를 비교한다.

공식 JavaScript 라이브러리는 이미지 또는 캔버스를 받아 예측할 수 있으므로 웹캠 기능을 붙일 필요가 없다.[2] 웹 앱에서는 관리자 등록 화면에서 실행하는 구성이 간단하다. 서버 일괄 처리가 필요하면 기존 서버 언어와 실행 환경에 맞추어 추론 방식을 별도로 정한다.

### 저장 필드 예시

| 필드 | 의미 |
|---|---|
| activity_id | 활동 ID |
| source_url | 모집 원문 |
| poster_hash | 포스터 변경·중복 확인용 값 |
| model_version | 분석에 사용한 모델 버전 |
| preprocessing_version | 입력 처리 규칙 버전 |
| field_scores | 전체 클래스 ID와 점수 |
| predicted_field | 1위 후보 |
| review_status | suggested / needs_review / confirmed |
| confirmed_fields | 원문 확인 후 확정한 서비스용 분야 태그; 예비 모델 클래스와 구분 |
| eligible_major_ids, major_requirement_text | 원문에 명시된 지원 가능 전공과 원문 조건; 추천 관련성과 별개 |
| eligibility_scope | 전공 무관 / 지정 전공 / 확인 필요 |
| eligibility_source_url, eligibility_verified_at | 지원 자격의 확인 근거와 시각 |
| activity_type | 공모전·서포터즈 등 |
| eligibility, deadline, region, participation_mode | 참여 조건 |

| verified_at | 모집 정보 최종 확인 시각 |

예측 결과와 관리자가 확정한 값을 구분한다. 재분석으로 관리자 수정값을 자동 덮어쓰지 않는다. 파일 해시·모델 버전·전처리 버전을 캐시 키로 사용한다.

외부 이미지 URL을 브라우저에서 직접 읽을 때는 CORS 제한이 발생할 수 있다. 실제 서비스에서 접근 가능한 이미지 저장 경로나 적절한 서버 이미지 제공 방식을 사용하고, 이미지·모델 로딩 실패는 ‘분석 실패’ 상태로 처리한다. 실패를 특정 분야나 점수 0의 정상 결과처럼 저장하지 않는다.

## 7. 불확실한 결과를 처리하는 기준

다음은 검증으로 조정해야 하는 초기 예시다.

- 상위 점수를 p1, 두 번째 점수를 p2라고 한다.
- p1 ≥ 0.80이고 p1 − p2 ≥ 0.20이면 ‘분야 후보 제안’ 상태로 저장한다.
- 그 외에는 ‘검토 필요’로 저장한다.
- 후보 제안 상태여도 첫 운영 버전에서는 관리자가 원문을 확인하여 확정한다.

0.80은 80% 정확도가 보장된다는 뜻이 아니다. 모델은 학습 범위 밖 이미지에도 높은 점수를 낼 수 있다. 검증에서는 임계값을 통과한 자료의 실제 정답률과 통과 비율을 함께 측정한다.

‘기타’ 클래스를 추가해도 모든 미지의 분야를 판별할 수 있는 것은 아니다. 기타에 넣을 자료 범위가 불명확하면 일단 검토 상태로 처리하고, 별도의 범위 밖 자료로 오분류를 평가한다.

미확정 분야만을 근거로 활동을 사용자에게서 숨기지 않는다. 모든 활동을 탐색할 수 있는 경로를 유지하고, 분야 미확정 항목은 별도 확인 상태로 표시한다.

### 8.4. 지원 자격과 전공 관련성을 구분한다

‘공학 전공과 관련 있는 활동’은 추천 점수의 근거다. ‘공학 계열 학생만 지원 가능’은 모집 원문에 있는 자격 조건이다. 전자는 다른 전공 학생의 참여를 제한하지 않는다.

- 마감·학년·재학 상태·학교·전공 제한은 원문으로 확인한 조건만 적용한다.
- ‘전공 무관’은 모든 전공에 대해 전공 제한을 두지 않는다는 뜻이며, 다른 자격 조건까지 통과한다는 뜻은 아니다.
- ‘관련 전공’처럼 범위가 불명확하면 확인 필요로 둔다. 추천용 연결표로 지원 가능 여부를 확정하지 않는다.
- 복수전공·부전공 인정 여부도 모집 조건을 따른다. 추천에 반영하는 것과 지원 자격으로 인정되는 것은 별개다.
- 특정 전공 제한이 없는 활동은 전공 관련성 점수가 낮아도 관심 분야가 맞으면 추천할 수 있다.
- 서울캠퍼스 소속만으로 현재 위치나 이동 가능 시간을 단정하지 않는다. 서울·수도권·온라인 선호를 제안하되 사용자가 바꿀 수 있게 한다.

### 8.5. 전공을 포함한 추천 점수

먼저 확인된 필수 조건을 처리한 뒤, 아래 점수를 계산한다. 모든 항목은 0~1이고 가중치는 초기 설계값이다.

추천 점수 = 100 × (wI × 관심 분야 일치 + wM × 전공 관련성 + 0.15 × 활동 유형 일치 + 0.10 × 참여 방식 일치 + 0.10 × 시간·기간 적합 + 0.10 × 활동 목표 일치)

| 선택 모드 | 관심 분야 wI | 전공 wM | 나머지 항목 합 |
|---|---:|---:|---:|
| 균형 — 기본 | 0.30 | 0.25 | 0.45 |
| 전공 중심 | 0.15 | 0.40 | 0.45 |
| 관심 확장 | 0.45 | 0.10 | 0.45 |
| 전공 미배정·미선택·연결 미확인 | 0.55 | 0 | 0.45 |

전공이 없는 사용자에게 전공 점수 0을 그대로 부과하지 않고 그 비중을 관심 분야로 옮긴다. 관심 분야까지 입력하지 않았다면 개인화 정보가 부족하다고 표시하고, 모집 중인 다양한 분야의 활동을 탐색할 수 있게 한다.

관심 분야 일치도는 사용자가 선택한 분야의 가중치를 합계 1로 정규화하고, 활동의 확정 분야와 겹치는 가중치를 더한다. 선호 우선순위를 받지 않았다면 균등하게 둔다.

전공 관련성은 다음처럼 계산한다.

1. 전공 m과 활동 a에 대해, 활동의 확인된 분야 태그 중 연결표 점수가 가장 높은 값을 r(m,a)로 둔다.
2. 추천에 반영할 전공이 하나면 M = r(m,a)다.
3. 여러 전공이면 M = Σ q(m) × r(m,a)로 계산한다. q의 합은 1이며, 기본은 선택한 전공 간 균등, 필요하면 학생이 비중을 조정한다.
4. 미배정·미확인 전공은 q 계산에서 빼고, 사용 가능한 전공이 하나도 없으면 위의 전공 미선택 가중치를 적용한다.
5. 활동 분야 자체가 미확정이면 M을 0.5의 중립값으로 임시 처리하고 정보 부족을 표시한다. 이때 ‘전공과 관련되어 추천’이라는 설명을 만들지 않는다.

여러 분야가 걸친 활동에 태그를 많이 붙여 점수가 무한히 늘지 않도록 전공별 최대 연결값을 사용한다. 여러 전공은 평균하기 때문에 전공을 더 많이 등록했다는 이유로 점수를 중복 가산하지 않는다.

#### 계산 예시

전기공학전공 학생이 IT·AI·데이터 0.6, 전기·전자·제조·공학 0.4를 관심 분야로 선택했다고 가정한다. 활동의 확인된 분야는 ENGINEERING과 IT_DATA이며, 개인 참여·온라인·단기 활동 조건을 충족한다.

- 관심 분야 일치 I = 1.0
- 전공 관련성 M = max(1.0, 0.5) = 1.0
- 활동 유형 T = 0.8, 참여 방식 P = 1.0, 시간·기간 D = 0.7, 목표 G = 1.0이라면
- 균형 모드 점수 = 100 × (0.30 + 0.25 + 0.12 + 0.10 + 0.07 + 0.10) = 94점

모든 수치는 설명용 가정이다. 94점은 실제 합격·만족 확률이 아니다. 전기공학전공 학생이 영상 제작을 선호하면 ‘관심 확장’ 모드에서 영상 활동도 충분히 추천되도록 한다.

추천 이유는 실제 반영한 사실로 생성한다. 예: ‘선택한 IT 관심 분야와 일치’, ‘전기공학전공과 연결된 공학 분야 활동’, ‘온라인 참여 가능’. 전공 때문에 학생이 특정 분야를 좋아한다고 설명하지 않는다. 모델 분류 점수를 사용자 적합 확률로 표시하지 않는다.

### 8.6. 구현용 데이터 구조와 갱신

| 테이블·설정 | 주요 필드 |
|---|---|
| majors | 내부 major_id, campus_id, college_id, 학부, 표시명, 적용 기간, active, source_url, verified_at |
| major_aliases | 이전 명칭·소속, 연결 major_id, 적용 학번·기간, 변경 근거 |
| user_majors | user_id, major_id, primary/double/minor, use_for_recommendation, preference_weight |
| fields | 서비스용 분야 ID와 표시명 |
| major_field_weights | major_id, field_id, weight, mapping_version, reason |
| activity_fields | activity_id, field_id, 확인 상태·근거 |
| activity_eligibility | 전공 제한 유무, 명시 전공, 모집 원문 조건, 확인 시각 |
| recommendation_config | 모드별 가중치, 버전 |
| recommendation_result | 사용자 프로필 버전, 활동 데이터 버전, 연결표 버전, 점수 구성, 생성 시각 |

major_id는 학교의 공식 학사 코드라고 주장하지 않는 서비스 내부 고정 ID를 사용한다. 명칭·소속이 바뀌어도 과거 사용자와 활동 기록을 보존한다. 학기 시작이나 공식 개편 공지 확인 시 목록을 갱신하고, 폐지·개편된 전공은 기존 학생을 위해 비활성 이력으로 남긴다.

기존 사용자의 전공을 추측하여 채우지 않는다. 새 필드는 null로 추가하고 프로필 보완 화면에서 선택하도록 한다. 사용자가 전공·관심 분야·모드를 바꾸면 추천 캐시를 갱신한다. 이미지 모델은 포스터가 같다면 전공 변경만으로 재실행하지 않는다.

## 9. 성능 평가와 완료 기준

학습 화면의 정확도 하나로 결과를 판단하지 않는다. 아래 두 작업을 따로 평가한다.

### A. 분야 분류 평가

- 전체 정확도와 분야별 정밀도·재현율, macro-F1을 기록한다.
- 혼동행렬로 어떤 분야끼리 자주 혼동되는지 확인한다.
- 항상 가장 많은 분야를 고르는 단순 기준보다 나은지 비교한다.
- 기관·행사 시리즈가 다른 포스터에서도 성능이 유지되는지 확인한다.
- 임계값 통과 자료의 정확도와 전체 중 통과한 비율을 함께 기록한다.
- 범위 밖 이미지를 높은 점수로 잘못 분류하는 사례를 따로 기록한다.

정밀도는 특정 분야라고 예측한 것 중 맞은 비율, 재현율은 실제 그 분야 자료 중 찾아낸 비율이다. macro-F1은 분야별 F1을 동등하게 평균한 값이다.

프로젝트 내부 목표의 예로 macro-F1 0.75 이상, 후보 제안 구간의 정확도 0.85 이상을 정할 수 있다. 이는 공식 기준이나 보장 수치가 아니다. 표본 수와 실제 결과를 함께 공개하고, 통과 비율이 매우 낮으면 정확도가 높아도 업무 절감 효과가 작은 점을 반영한다.

### B. 추천 평가

- 단과대학별 학생, 복수전공·부전공 학생, 전공 미배정 학생을 포함한 서로 다른 사용자 프로필을 구성한다. 초기 10~20개 프로필은 예비 평가이며 전공별 결과를 일반화하기에는 부족할 수 있다.
- 동일한 관심 분야에서 전공만 바꾼 경우와, 동일 전공에서 관심 분야·추천 모드만 바꾼 경우를 비교한다.
- 전공 항목을 제외한 기존 추천과 개정 추천의 Precision@5를 비교한다. 전공별 표본 수와 만족도·노출 활동 다양성도 함께 기록한다.
- 전공 무관 활동이 부당하게 제외되지 않는지, 전공 제한 활동의 자격 검사가 추천 연결표와 독립적으로 작동하는지 확인한다.
- 사용자나 평가자가 실제로 적합한 활동을 먼저 판단한다.
- 상위 5개 중 적합한 활동의 비율인 Precision@5를 측정한다.
- 마감·자격 등 확인된 필수 조건을 위반한 추천 건수를 확인한다.
- ‘티처블 머신 후보 사용’, ‘분야 후보 없이 추천’, ‘관리자 정답 분야 사용’을 비교한다.

마지막 비교에서 관리자 정답 분야는 추천 로직 자체를 평가하는 기준이다. 모든 분야를 관리자가 확정한 뒤 추천한다면, 티처블 머신의 주효과는 추천 정확도 상승보다 분류 입력 시간 절감일 수 있다. 이 경우 등록 1건당 검토 시간과 후보 수정률도 측정한다.

### 기능 완료 체크리스트

- [ ] 새 포스터 등록 시 모델이 실행되고 전체 결과가 저장된다.
- [ ] 학습·서비스 전처리가 동일하다.
- [ ] 불확실한 결과와 실행 실패가 구분된다.
- [ ] 관리자 수정값과 모델 예측값이 분리되어 있다.
- [ ] 확인된 참여 조건이 추천에 적용된다.
- [ ] 모델 점수를 사용자 적합도처럼 표시하지 않는다.
- [ ] 모델 업데이트 시 관리자 확정값이 보존된다.
- [ ] 새 기관·새 행사 포스터로 평가한 결과가 있다.
- [ ] 공식 서울캠퍼스 선택 목록과 구 명칭·소속 이력이 구분된다.
- [ ] 모든 등록 전공에 분야 연결이 있고, 미배정·미선택 사용자의 추천이 가능하다.
- [ ] 복수전공·부전공 선택과 추천 반영 여부를 변경할 수 있다.
- [ ] 예비 모델 밖 분야도 관리자 태그로 등록·추천할 수 있다.
- [ ] 전공 관련성과 모집 원문의 전공 지원 자격이 분리된다.
- [ ] 전공·관심·모드 변경 시 추천이 갱신되고 가중치 합은 1이다.

## 10. 구현 순서와 발표 시 설명

1. **목록·분류 기준 확정:** 공식 서울캠퍼스 전공 목록과 12개 서비스 분야, 전공별 연결표를 등록한다. 4개 예비 모델 클래스와 서비스 분야를 구분한다.
2. **예비 실험:** 분야별 약 50개 행사로 이미지 분류의 가능성을 확인한다.
3. **데이터 보완:** 분야별 150~200개 수준으로 확대하고 그룹 단위로 분할한다.
4. **학습·검증:** 전처리를 통일하고 외부 검증 자료로 모델과 임계값을 선택한다.
5. **기존 프로그램 연동:** 활동 등록 화면에 모델 실행·저장·관리자 수정 기능을 추가한다.
6. **추천 연결:** 전공·복수전공·관심 분야·추천 모드를 입력받고, 전공 관련성을 포함한 점수와 실제 추천 이유를 표시한다.
7. **최종 평가:** 보관해 둔 시험 포스터와 사용자별 추천 결과를 평가한다.

발표에서는 “티처블 머신으로 대외활동 포스터의 시각적 특징을 학습해 분야 후보를 제시하고, 확인된 모집 정보와 상명대학교 서울캠퍼스 학생의 전공·관심 분야·참여 선호를 결합해 활동을 추천한다”고 설명한다. 티처블 머신이 포스터의 모든 문장을 이해하거나 사용자 성격을 직접 학습했다고 설명하지 않는다.

추가 학습은 관리자 수정 자료를 모아 일정량이 쌓였을 때 수행한다. 수정했다고 배포된 모델이 즉시 바뀌는 것은 아니며, 재학습·검증·내보내기·모델 교체가 필요하다.
