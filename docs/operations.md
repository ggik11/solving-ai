# 운영 노트

> 5단계(운영·검증)에서 정식으로 채웠다. 법률 준수를 보장한다고 쓰지 않는다 — "실제로 구현된
> 것"과 "운영 전에 사람이 검토·결정해야 하는 것"을 분리해서 표시한다.

## 1. 관리자 초기 설정 (첫 관리자 지정)

이 앱에는 "회원가입하면서 관리자로 가입" 같은 경로가 **의도적으로 없다** — `user_roles` 테이블은
일반 사용자가 자기 자신을 추가할 수 없도록 RLS로 막혀 있다(`tests/rls/admin_write.test.ts`,
`tests/rls/reports_and_moderation.test.ts`로 검증). 로컬 개발 환경은 `supabase/seed.sql`이
`admin@smu.ac.kr` 계정을 자동으로 관리자로 등록하지만, **이 시드는 운영 환경에 적용하지 않는다**
(아래 5절 "환경 분리" 참조).

운영 환경에서 첫 관리자를 지정하는 방법 — Supabase 대시보드의 **SQL Editor**(또는 `psql`로 직접
연결)에서, 그 사람이 먼저 한 번 로그인(매직링크)해 `profiles` 행이 생성된 뒤 다음을 실행한다:

```sql
-- 1. 지정할 사람의 profile id를 nickname 또는 (운영자만 아는) 다른 단서로 찾는다.
select id, nickname, created_at from public.profiles order by created_at desc limit 20;

-- 2. 그 id를 user_roles에 추가한다.
insert into public.user_roles (profile_id, role) values ('<위에서 찾은 id>', 'admin');
```

둘째 관리자부터는 **이미 관리자가 된 계정이 직접 SQL로 추가**하거나, Supabase 대시보드 접근
권한이 있는 사람이 같은 방식으로 추가한다. `/admin` 화면 안에 "관리자 추가" 기능은 없다(관리자
권한 관리 자체를 앱 UI에 노출하지 않기로 한 설계 선택 — 실수로 권한을 남발하는 것을 막는다).

## 2. 신고 처리 절차

1. `/admin/reports`에서 상태별(접수/검토 중/조치/기각) 목록을 확인한다.
2. 신고 사유(스팸·도배/욕설·혐오/부적절한 콘텐츠/사기·허위/기타)와 신고자가 남긴 설명을 읽는다.
3. 대상이 `chat_message`(채팅 메시지)면 "신고된 메시지 보기" 버튼으로 **그 메시지 전후 3개씩만**
   확인한다 — 신고와 무관한 전체 채팅 기록을 열람하는 기능은 의도적으로 만들지 않았다. 이 열람
   행위 자체도 감사 로그(`view_reported_message_context`)에 남는다.
4. 대상이 `profile`(사용자)이면 `/admin/accounts`에서 닉네임으로 검색해 이력을 가늠한다(단,
   프로필에는 실명·이메일·학번이 없으므로 신고 내용과 신고자 설명이 사실상 유일한 판단 근거다 —
   오탐·악의적 신고 가능성을 염두에 두고 처리한다).
5. 처리 메모를 남기고 상태를 변경한다(`update_report_status` — 운영자만 가능, 모든 변경이
   감사 로그에 남는다):
   - **검토 중**: 추가 확인이 필요할 때.
   - **조치**: 계정 정지 등 실제 조치를 취했을 때(아래 3절).
   - **기각**: 근거가 부족하거나 규정 위반이 아니라고 판단했을 때.
6. 신고가 반복되는 대상이면 `/admin/reports`에서 같은 `target_id`로 필터링(현재는 화면에 필터가
   없으므로 목록을 눈으로 훑거나 Supabase Studio에서 직접 조회)해 패턴을 확인한다.

## 3. 제재 (계정 정지)

- `/admin/accounts`에서 닉네임으로 검색 → 정지 사유를 적고 "정지" 버튼.
- 정지된 계정은 **DB 레벨 트리거**(`_enforce_active_account`, 모든 주요 쓰기 테이블에 적용)로
  지원·메시지 전송·매칭 참가·파티 생성 등 쓰기 동작이 전부 거부된다(`ACCOUNT_SUSPENDED`). 기존
  데이터 조회(읽기)는 막지 않는다 — 완전한 접근 차단이 필요하면 별도 검토가 필요하다(8절 참고).
- **운영자 계정은 이 화면에서 정지할 수 없다**(`CANNOT_SUSPEND_ADMIN` — 안전장치). 운영자를
  제재해야 하는 상황이면 먼저 `user_roles`에서 그 사람의 관리자 행을 지운 뒤 일반 정지 절차를
  따른다.
- 정지 해제도 같은 화면에서 한다. 정지 ↔ 해제 모두 감사 로그(`account_suspended`/
  `account_unsuspended`)에 사유와 함께 남는다.
- **탈퇴와의 차이:** 탈퇴(`withdraw_account`)는 사용자 본인만 할 수 있고 프로필을 비식별화한다.
  정지는 운영자만 할 수 있고 프로필 정보는 그대로 둔 채 쓰기만 막는다(복구 가능).

## 4. 백업과 복원

이 저장소는 백업 자동화 코드를 포함하지 않는다 — 호스팅 선택에 따라 제공되는 기능을 그대로
쓰는 것을 전제로 문서화한다.

- **Supabase 클라우드(권장 운영 방식)**: Pro 이상 플랜은 매일 자동 백업(PITR은 더 상위 플랜)을
  제공한다. 대시보드의 **Database → Backups**에서 복원 시점을 선택해 복원한다. 무료 플랜은 자동
  백업이 없거나 보존 기간이 매우 짧으므로, 실제 사용자 데이터를 다루기 전에 플랜을 확인한다.
- **자체 호스팅/로컬**: `pg_dump`로 수동 백업한다.
  ```bash
  pg_dump "postgresql://postgres:<password>@<host>:5432/postgres" -F c -f backup.dump
  # 복원
  pg_restore -d "postgresql://postgres:<password>@<host>:5432/postgres" --clean backup.dump
  ```
- **백업에 포함되는 것/안 되는 것**: `pg_dump`/Supabase 백업은 `auth.users`(이메일, 인증 상태)를
  포함한다 — 백업 파일 자체를 서비스 운영자 외 누구와도 공유하지 않는다. `storage` 버킷(이 MVP는
  스토리지를 쓰지 않는다)은 DB 백업과 별도로 관리해야 한다.
- **아직 결정하지 않은 것**: 백업 보존 기간, 백업 암호화·접근 통제, 복원 리허설 주기. 실제
  운영 전에 운영자가 정책으로 정해야 한다(법정 의무 기간이 있는지는 이 문서가 판단하지 않는다).

## 5. 보존과 삭제 정책

**현재 구현된 것:**
- 회원 탈퇴(`withdraw_account`) 시 프로필이 비식별화된다(닉네임 "탈퇴한 사용자", 자기소개·
  포트폴리오 링크·참여 조건 등 선택 정보 삭제, 전공·관심분야·기술·가능 시간 행 삭제). `auth.users`
  행 자체와 과거 채팅 메시지·파티 이력은 삭제하지 않는다(팀에 남은 다른 사용자의 대화 맥락을
  보존하기 위해 — 지시서 8장 "보존 정책에 따라 과거 메시지가 팀에 남을 수 있음을 안내").
- 신고(`reports`)·감사 로그(`audit_logs`)는 자동 삭제되지 않는다 — 무기한 보존된다.
- 활동(`activities`)·파티(`parties`)·채팅(`chat_messages`) 등 일반 데이터도 자동 삭제되지
  않는다.

**아직 정책으로 정하지 않은 것(운영 전 결정 필요):**
- 탈퇴한 계정의 익명화된 흔적(비식별화된 `profiles` 행, 과거 채팅 메시지)을 얼마나 보존할지.
- 신고·감사 로그를 몇 년 보존할지, 또는 보존 기간을 두지 않을지.
- 종료된(`cancelled`/`completed`) 활동·파티의 데이터를 정리할지.
- 삭제 요청(개인정보보호법상 "삭제권" 등 관련 법규가 요구할 경우) 처리 절차 — 현재는 수동으로
  Supabase Studio에서 해당 사용자의 `profiles` 행과 관련 데이터를 운영자가 직접 처리해야 한다.
  전용 "관리자가 사용자를 완전히 삭제" 기능은 이번 범위에 없다.

이 문서는 "법적으로 N일/N년 보존해야 한다"처럼 법정 의무 기간을 단정하지 않는다 — 실제 서비스로
전환하기 전 법무 검토를 거쳐 운영 정책으로 명문화해야 할 항목으로만 남겨둔다.

## 6. 개인정보 수집 목적과 공개 범위 (초안 — 법무 검토 전)

**수집하는 것:**
- 이메일 주소(`auth.users.email`) — 로그인(매직링크) 목적. 다른 사용자에게 공개되지 않는다.
- 닉네임, 대학/캠퍼스/전공(자기기입), 학년, 자기소개, 포트폴리오 링크, 관심분야, 희망 활동
  유형, 수행 가능 역할, 참여 조건(온/오프/혼합·지역·주당 가능 시간), 가능한 시간대 — 온보딩에서
  사용자가 직접 입력. 목적: 활동 추천 계산, 파티·매칭 상대 탐색.
- 차단·신고 기록, 채팅 메시지, 파티·매칭 참여 이력 — 서비스 핵심 기능(팀 구성, 신뢰·안전) 운영
  목적.

**수집하지 않는 것(지시서 3장 원칙 그대로 유지):** 실명, 학번, 전화번호. 이 서비스는 닉네임만
쓰고, 로그인에 필요한 이메일 외에는 식별 정보를 요구하지 않는다.

**공개 범위:**
- `profiles.profile_visibility`(공개/팀원만/비공개, 기본값 팀원만)로 사용자가 직접 조절한다.
- 닉네임은 같은 파티·채팅방 멤버에게 항상 보인다(팀 구성·소통에 필요).
- 이메일·학년·전공 상세 등은 본인과 운영자만 조회 가능(RLS로 강제).
- 신고 처리 과정에서 운영자가 신고 대상·신고자의 닉네임과 신고 내용을 볼 수 있다(2절 참조).

**아직 법무 검토를 거치지 않은 것:** 이 절은 코드가 실제로 수집·저장하는 항목을 정리한 것이지,
개인정보보호법(또는 해당 관할 법규)상 요구되는 고지·동의 절차를 완전히 갖췄다는 뜻이 아니다.
실제 서비스 운영 전에는 (a) 개인정보처리방침 문서 작성, (b) 수집 항목별 동의 절차, (c) 제3자
제공 여부(현재 없음) 명시, (d) 위 5절의 보존 기간을 포함해 법무 검토를 받아야 한다.

## 7. 로그인/OTP 빈도 제한과 jwt_expiry — 로컬 설정이 운영(클라우드)에도 적용되는 방법

`supabase/config.toml`은 **로컬 `supabase start` 스택**을 설정한다. 이 파일을 Supabase Cloud에
연결(`supabase link`)한 뒤 `supabase db push`로 보내는 것은 **마이그레이션(`supabase/migrations/`,
즉 DB 스키마)뿐**이다 — `[auth]` 섹션(이메일/OTP 빈도 제한, `jwt_expiry` 등)은 DB 마이그레이션이
아니라 **Auth 서비스 자체의 설정**이므로, CLI로 로컬 `config.toml`을 클라우드 프로젝트에 자동으로
동기화해 주지 않는다(동기화하는 `supabase config push`류 명령이 CLI 버전에 따라 있을 수 있지만,
어느 쪽이든 **Dashboard에서 직접 확인하는 것이 가장 확실하다** — 자동 동기화를 가정하고 로컬 값이
알아서 적용됐을 거라 믿지 않는다).

**현재 로컬 설정값(`supabase/config.toml`)과 그 의미:**

| 설정 | 로컬 값 | 비고 |
|---|---|---|
| `auth.jwt_expiry` | 300(초) | 3600(기본 1시간)에서 줄임 — 탈퇴·강퇴 후 이미 열린 Realtime 연결이 새 메시지를 계속 수신할 수 있는 노출 구간을 좁히기 위해(4-B에서 결정, 아래 8절 참조) |
| `auth.email.max_frequency` | `1s` | 같은 주소로 확인/재설정 메일을 다시 보내기까지 최소 대기 시간. **로컬 개발 편의를 위해 느슨하게 둔 값이 아니라 기본값 그대로다** |
| `auth.rate_limit.email_sent` | 100(시간당) | **로컬 전용으로 기본값(2)에서 올려둔 값**(`config.toml`에 주석으로 명시) — 로컬 SMTP가 Inbucket/Mailpit로만 가고 실제 메일을 안 보내기 때문에 테스트 편의상 올렸다 |
| `auth.rate_limit.sign_in_sign_ups` | 30(5분·IP당) | 매직링크 로그인 요청 포함 |
| `auth.rate_limit.token_verifications` | 30(5분·IP당) | 매직링크/OTP 검증 시도 포함 |

**운영(클라우드) 전환 시 할 일:**
1. Supabase 대시보드 → **Authentication → Rate Limits**에서 `email_sent`를 로컬의 완화된 값(100)이
   아니라 **운영에 맞는 보수적인 값**(기본값 2, 또는 실제 가입/문의량을 보고 조정)으로 설정한다.
   `sign_in_sign_ups`·`token_verifications` 등 나머지 빈도 제한도 이 화면에서 직접 확인·조정한다.
2. Supabase 대시보드 → **Authentication → Sessions**(또는 JWT 설정 화면, 버전에 따라 위치가
   다를 수 있음)에서 **JWT expiry를 300초로 설정**한다 — 이 값이 로컬과 다르면 8절의 완화 효과가
   운영에는 적용되지 않는다.
3. 실제로 적용됐는지 확인하는 방법: 매직링크로 로그인한 뒤 발급된 토큰을 디코드해(예:
   https://jwt.io 또는 `JSON.parse(atob(token.split('.')[1]))`) `exp - iat`가 300에 가까운지
   확인한다(매 요청 토큰을 직접 공유하지 말고 자신의 세션으로만 확인할 것).
4. 운영 메일 발신자(SMTP)를 반드시 별도로 설정한다 — 로컬 설정의 Inbucket/Mailpit는 테스트
   전용이며 실제 메일을 보내지 않는다. 클라우드 프로젝트는 기본 제공되는 Supabase 발신 한도가
   매우 낮으므로(시간당 소수 건) 실제 서비스는 커스텀 SMTP(SendGrid, AWS SES 등) 연결이
   사실상 필수다.

## 8. Realtime 연결 차단 한계

### 탈퇴 후 이미 열린 Realtime 연결의 서버 측 차단 한계

### 배경

팀 채팅의 Realtime 전달은 Broadcast-from-Database + `realtime.messages` RLS로 구현돼 있다
(architecture.md 11.2절). 탈퇴·강퇴된 사용자는 `is_party_member()`가 더 이상 참이 아니므로
새 구독은 거부되고, `ChatRoomClient`의 15초 하트비트가 `mark_chat_read`를 호출해
`NOT_A_MEMBER`를 받으면 클라이언트가 스스로 구독을 끊는다(architecture.md 11.4절).

### 재검토 계기

4-B 작업 중 `@supabase/realtime-js`의 공식 문서를 다시 확인했다:

> "Client access policies are cached for the duration of the connection. Realtime updates the
> access policy cache for a client based on your RLS policies when a client connects to Realtime
> and subscribes to a Channel, **or when a new JWT is sent to Realtime from a client via the
> access_token message.**"

즉 private 채널의 구독 인가는 **연결마다 캐시**되고, **메시지마다 다시 검사되지 않는다** — 새
JWT가 전달될 때(최초 연결, 로그인, 토큰 갱신)만 재평가된다. `@supabase/supabase-js`
소스(`_handleTokenChanged`)를 확인하면 `TOKEN_REFRESHED`/`SIGNED_IN`/`INITIAL_SESSION` 이벤트마다
`realtime.setAuth(새_토큰)`을 호출해 이 캐시를 갱신시킨다 — 토큰 자동 갱신은 `jwt_expiry`
설정을 기준으로 그보다 먼저 일어난다.

**결론:** 브라우저 탭을 이미 열어 둔 채로 탈퇴·강퇴당한 사용자는, 클라이언트 JS(하트비트)가
정상 동작하는 한 곧바로 끊기지만(1차 방어선), 만약 그 JS가 변조되거나 실행되지 않는다면
(예: 오프라인, 확장프로그램 차단, 의도적 조작) **다음 토큰 갱신 시점까지는 이미 열린 구독으로
브로드캐스트를 계속 수신할 수 있다.** 이는 RLS 설계의 허점이 아니라 Realtime의 연결 단위
캐싱 동작 자체의 특성이다.

### 적용한 완화책

`supabase/config.toml`의 `jwt_expiry`를 기본값 3600초(1시간)에서 **300초(5분)**로 줄였다.
토큰이 더 자주 갱신되므로, 위 노출 구간(클라이언트 하트비트가 동작하지 않는 최악의 경우)이
**최대 1시간에서 최대 5분으로** 줄어든다.

- 트레이드오프: 인증 서버로 가는 토큰 갱신 요청이 더 잦아진다(세션당 1시간에 1번 → 5분에
  1번). 로컬/소규모 데모 스케일에서는 무시할 수 있는 비용이다.
- 이 값을 조정해도 **근본 해결은 아니다** — 아래 "남는 한계" 참조.

### 남는 한계 (완화 후에도 남는 것)

1. **완전한 즉시 차단이 아니다.** `jwt_expiry`를 아무리 줄여도 0초로는 못 만들므로, 이론상
   최대 `jwt_expiry`만큼의 메시지 수신 노출 구간이 항상 남는다. 완전히 없애려면 Realtime이
   메시지마다(또는 매우 짧은 주기로) 서버 쪽에서 연결을 강제로 재검사/차단하는 기능이
   필요한데, 표준 Supabase 클라이언트 API로는 "특정 연결을 서버에서 강제로 끊기"가 노출돼
   있지 않다(관리용 REST/함수로 별도 구현이 필요하며 이번 범위에서는 하지 않았다).
2. **전송(쓰기)은 이미 완전히 막혀 있다.** `send_chat_message`/`mark_chat_read`는 매 호출마다
   서버에서 멤버십을 다시 확인하므로(SECURITY DEFINER 함수, 캐시 없음), 탈퇴한 사용자는
   토큰 갱신을 기다릴 것도 없이 즉시 전송·읽음 처리를 할 수 없다. 이번 한계는 **수신(읽기)**
   에만 해당한다.
3. **실제 공격 가치가 낮다.** 수신만 가능하고 전송은 불가능하므로, 공격자가 얻는 것은 "이미
   알고 있던 채팅방에서 짧은 시간 동안 새 메시지를 더 보는 것"뿐이다 — 데모/MVP 위협
   모델에서는 낮은 심각도로 판단했다.
4. **5단계에서 재검토할 사항:** (a) `jwt_expiry`를 더 줄일지(예: 60초) 비용 대비 효과 측정,
   (b) Supabase Management API/Realtime Admin 채널로 특정 연결을 강제 종료하는 방법이
   생겼는지 확인, (c) 팀 이탈 이벤트 발생 시 해당 활동의 모든 구성원에게 `access_token`
   재전송을 강제로 트리거하는 클라이언트 측 보강(예: 브로드캐스트로 "재인증 필요" 신호를
   보내 즉시 `supabase.auth.refreshSession()`을 호출하게 하는 방법)의 실효성 검토.

## 9. 알려진 제한

기능 단위의 알려진 제한(추천 계산의 미상 처리, CSV 가져오기의 정확 일치 전용 매칭 등)은
`PROGRESS.md`의 "알려진 제한 / 다음 단계로 미룬 것" 절에 모아뒀다. 여기서는 **운영 관점**의
제한만 추가로 적는다.

1. **pg_cron(빠른 매칭 워커)이 단일 장애점이다.** `run_match_worker`는 Supabase 프로젝트 안의
   `pg_cron` 확장 하나로만 매분 실행된다. Postgres 자체가 재시작되거나 `pg_cron` 확장이
   비활성화되면 매칭이 조용히 멈춘다 — 별도 모니터링/알림이 없다. `npm run worker:match`로
   수동 실행은 가능하지만 자동 감지·재시작 체계는 없다.
2. **운영 메일 발신자가 기본값 그대로면 사실상 쓸 수 없다.** 7절 참조 — 커스텀 SMTP 연결 전
   가입이 몰리면 매직링크 발송이 막힌다.
3. **관리자 추가는 전적으로 수동(SQL)이다.** 1절 참조 — 관리자 인수인계 절차를 팀 차원에서
   별도로 정해야 한다(예: 누가 Supabase 대시보드 접근 권한을 갖는지).
4. **신고·제재 처리에 SLA(처리 기한)가 없다.** `/admin/reports`는 상태만 관리할 뿐, 기한 초과
   알림이나 담당자 배정 기능은 없다. 운영자가 여러 명이면 역할 분담을 팀 차원에서 정해야 한다.
5. **모니터링·에러 추적이 연결돼 있지 않다.** Sentry 등 에러 추적 서비스가 설정돼 있지 않다 —
   프로덕션에서 발생하는 런타임 에러는 Vercel(또는 선택한 호스팅)의 기본 로그에만 남는다.
   지시서 11장 원칙대로 이메일·토큰·채팅 본문은 로그에 남기지 않지만(서버 액션 에러 메시지는
   `DbError`로 가공된 사용자 메시지만 노출), 별도 에러 추적 도구 연결은 이번 범위 밖이다.
6. **부하·용량 테스트를 하지 않았다.** 동시 사용자 수, DB 커넥션 풀 크기, Realtime 동시 접속
   한도에 대한 실측 데이터가 없다 — 실제 트래픽 규모가 정해지면 별도로 검증해야 한다.

## 10. 모델 교체 절차

운영 환경에서 포스터 분류 모델을 처음 배포하거나 교체할 때의 절차다. 개발 중심 설명(티처블
머신 학습·내보내기 순서)은 README.md "포스터 분류 모델 교체 절차" 절을 참고하고, 여기서는
**운영 관점**(배포 순서, 되돌리기, 실패 시 영향)만 적는다.

1. **클래스 구성은 모델보다 먼저 존재해야 한다.** `classifier_class_sets`/
   `classifier_class_set_classes`는 마이그레이션으로만 추가한다(시드 아님 — 운영 DB에도
   적용되어야 하기 때문). 분야 구성을 바꾸지 않는 한(클래스 추가/제거) 기존 활성 구성
   (`pilot-7-v1`, 이전 `pilot-4-v1`/`pilot-6-v1`도 비활성으로 남아 있음)을 그대로 쓰면 되고,
   이 단계는 생략할 수 있다.
2. **모델 파일 배포 → 등록 → 평가 순서를 지킨다.** `public/models/poster-classifier/`에 새
   파일을 배포한 직후에는 아직 `model_class_field_map`에 새 `model_version`의 연결표가 없다 —
   `/admin/model-lab`에서 관리자가 직접 "등록"을 눌러야 후보 제안이 켜진다. 즉 **배포와 등록
   사이에는 "모델은 떠 있지만 후보 제안은 꺼져 있는" 짧은 공백이 있을 수 있다** — 이 기간에도
   분석은 `needs_review`/수동 선택으로 자연스럽게 넘어가므로(체크리스트 6번) 서비스가 멈추지는
   않는다.
3. **등록은 labels가 선택한 클래스 구성과 정확히 일치할 때만 서버(DB 함수)가 허용한다.**
   화면의 버튼 비활성화는 보조 수단일 뿐이고, 실제 가드는 `register_classifier_model()` 안의
   `LABELS_MISMATCH` 체크다 — 잘못된 라벨로 내보낸 모델은 등록 자체가 거부된다.
4. **되돌리기:** 새 모델 등록 후 문제가 발견되면, 이전 모델 파일을 `public/models/
   poster-classifier/`에 다시 배포하고 그 버전을 다시 "등록"하면 된다(이미 등록된 적 있는
   버전이면 재등록은 갱신일 뿐 거부되지 않는다 — 멱등). `model_class_field_map`은 모델 버전별로
   쌓이므로 과거 버전의 연결표를 지우지 않는 한 과거 분석 기록은 항상 해석 가능하다.
5. **판정 임계값(`app_settings.poster_classifier`)은 모델 교체와 별개로 조정될 수 있다.**
   새 모델을 등록했다고 임계값이 자동으로 바뀌지 않는다 — `/admin/model-lab`의 평가 결과를 보고
   운영자가 직접 `suggest_min_top_score`/`suggest_min_margin`을 조정한다(일반 사용자는 수정할
   수 없음, RLS로 강제).
